# Актуальное ТЗ и общий контракт проекта #79-lite

Этот файл описывает целевой MVP. Не утверждай, что всё ниже уже реализовано. Сначала прочитай применимые инструкции и актуальный код. При конфликте с официальным заданием приоритет у задания; при конфликте с работающим интерфейсом участник 1 согласует минимальную совместимую поправку для всех троих.

## Статус документа и приоритеты

Это консолидированный проектный план по видимой переписке, а не результат аудита репозитория. Исходное задание организаторов сохранено в `TASK_ORIGINAL.md`, история обсуждения — в `SESSION_CONTEXT.md`.

В рамках проектных документов: явные актуальные указания команды и официальное задание → согласованный действующий контракт → это ТЗ → планы ролей. История обсуждения не переопределяет актуальные требования. Применимые системные инструкции, AGENTS.md, настройки доступа и безопасности сохраняют свой приоритет.

Если код расходится с заданием, это дефект, а не повод объявить код новым заданием. Если отличается только название совместимой функции, сохранить работающий интерфейс и документировать соответствие. Новые предпочтения ниже — проектные решения команды/предложения из переписки, а не дополнительные требования организаторов.

Все примеры профилей, цен и дат из переписки условные до проверки JSONL. Ни репозиторий, ни JSONL при составлении этого пакета не были предоставлены. Никакая функция не объявлена реализованной.

## 1. Продукт и оценка

Заказчик event-агрегатора уже выбрал тип мероприятия и каталог своего города. Помогаем выбрать до 3 подрядчиков из этого каталога. Не расширяем город, не добавляем неподходящих ради количества, не бронируем и не отправляем заявки.

Вход: город, дата, мероприятие, категория, бюджет в ₸; необязательно длительность и язык. Выход: до 3 карточек с именем, выбранной категорией, городом, ценой «от» и 1–2 предложениями объяснения.

Приоритет: качество объяснений → честная работа с редкими, занятыми и пустыми категориями → скорость → UI. Оценка: соответствие и работоспособность 25; техническая реализация 25; README и воспроизводимость 25; ценность 15; развитие и оригинальность 10. Это максимумы критериев, не обещанные баллы команды.

## 2. Данные и честные ограничения

Исходный файл: `hackathon-dataset-anonymized.jsonl`, по заданию 66 профилей. Есть CSV и HTML-превью, но для приложения выбираем один источник истины — JSONL. Сам файл в пакет планов не включён. Если его нет в проекте, явно сообщить: реальные результаты и демо пока не подтверждены. Не заменять источник незаметно выдуманными профилями.

Поля: `id`, `anon_name`, `categories`, `city`, `price_from_kzt`, `event_formats`, `languages`, `max_hours`, `busy_dates`, `description`, `synthetic`, `city_imputed`, `price_imputed`.

Города по заданию: Алматы, Астана, Зарубежье. Форматы: свадьба, той, корпоратив, конференция, юбилей, день рождения. Языки: русский, казахский, английский. Реальные написания и типы проверить в файле.

Окно календаря: 23.09.2026–31.12.2026 включительно. В MVP ограничить выбор даты этим окном. Для даты вне окна показывать ошибку ввода, не считать всех свободными. Сентябрь–ноябрь: по условию заняты 30–50% дней, декабрь: 70–80%; это контекст, а не основание вычислять доступность без `busy_dates`.

`max_hours=null` означает, что работа не привязана к присутствию на площадке. Не исключать за длительность и не объявлять такого подрядчика работающим «безлимитно».

`price_from_kzt` — нижняя граница, а не окончательная цена. Условие допуска: эта граница не выше бюджета. В тексте: «начальная цена ниже лимита на …». Нельзя обещать итоговую стоимость, реальную экономию или гарантированный остаток денег. `price_imputed=true` и `city_imputed=true` отображать как значения, проставленные при подготовке данных.

В исходном наборе 13 полностью синтетических профилей. `synthetic=true` помечать «Синтетический профиль», `false` — «Профиль исходного каталога», не «проверенный реальный подрядчик». Добавленные командой записи, если они вообще понадобятся, хранить отдельно, помечать `synthetic=true` и дополнительно «Добавлен командой». Не делать их для заполнения TOP-3. Не назначать баллы доверия по флагу synthetic.

Категории и числа в задании относятся к набору целиком, а не к каждому городу: Ведущий — 15, Фотограф — 12, Банкетный зал — 8; Флорист, Декоратор, Подарки и сувениры, Ведущий церемонии, Фото и видеобудки, Отель, Инструменталист — по 3. На реальном файле пересчитать распределение по городу и категории.

## 3. Пять болей → код → проверка

| Боль | Реализация | Проверка |
|---|---|---|
| Непонятно, почему рекомендован | Структурированные факты и объяснение, соответствующее реальным правилам выбора | Факт можно найти в полях профиля или запроса |
| Рекомендован неподходящий | Все обязательные условия проверяет код до ranking | Занятый, дорогой, неверный формат/язык/длительность исключены |
| Объяснения одинаковые | Конкретные значения и отличительный релевантный факт | Без имён можно сопоставить карточки; если данных не хватает — честное ограничение |
| Пустая выдача ничего не объясняет | Три бизнес-статуса, статистика исключений, сообщение для 1–2 результатов | Нет пустого экрана и двойного подсчёта причин |
| Случайный порядок | Фиксированный scoring, режим, данные и tie-break | Повторы и перестановка исходных строк не меняют результат |

## 4. Единый интерфейс

Ниже — договорённость для нового/несогласованного кода. Если уже есть совместимый работающий интерфейс, участник 1 фиксирует его эквивалент и сообщает всей команде. Остальные не меняют контракт самостоятельно.

```python
query = {
    "city": "Алматы",
    "date": "2026-11-14",   # ISO YYYY-MM-DD
    "event_type": "свадьба",
    "category": "Ведущий",
    "budget": 300000,       # > 0
    "duration": 6,          # > 0 или None
    "language": "казахский" # или None
}
```

Пример показывает форму запроса, но НЕ подтверждённое демо.

Публичные функции:

```python
# Участник 1
load_contractors(path) -> list[dict]
recommend(query, contractors) -> dict

# Участник 2
rank_candidates(candidates, query) -> list[dict]
build_cards(top_candidates, query) -> list[dict]
```

`rank_candidates` получает только допустимых, возвращает ВСЕХ в устойчивом порядке. Профили копируются; к копиям добавляются `score`, `score_breakdown`, `evidence`. Исходные профили не мутировать. Evidence хранит ссылку на поле-источник и значение, для описания — буквальный фрагмент текста.

`recommend` один раз берёт первые 3 и передаёт их в `build_cards`. Эта функция не меняет состав или порядок, а добавляет `category` (выбранную пользователем), `explanation` и сохраняет исходные поля и флаги. Все карточки возвращаются в `results`.

```python
response = {
    "status": "success",  # либо category_not_found / no_matching_candidates
    "query": query,
    "results": [],        # list[dict], после реального подбора 0–3 карточки
    "stats": {
        "city_category_total": 0,
        "eligible_count": 0,
        "returned_count": 0,
        "rejected_first_reason": {
            "busy": 0,
            "over_budget": 0,
            "wrong_format": 0,
            "wrong_language": 0,
            "too_short": 0
        }
    },
    "rejections": [], # id, anon_name, primary_reason, reasons
    "message": "...", # готовый человеческий текст из ядра
    "meta": {
        "ranking_method": "...", # фактический, не рекламный
        "dataset_hash": "...",
        "scoring_version": "..."
    }
}
```

Нули и пустой results выше иллюстрируют схему, не корректный результат success. Инвариант: success только при 1–3 results; два остальных статуса — только при пустом results. Ошибка файла, API или невалидный ввод не маскируются бизнес-статусом «кандидатов нет».

UI отображает этот ответ, не пересчитывает отбор, score или причины. Дату преобразует в ISO, отсутствие необязательных параметров — в None.

## 5. Фильтры и причины

Сначала `city` и наличие выбранной категории в `categories`. Нет таких записей → `category_not_found`.

Внутри найденной группы проверять в фиксированном порядке: занятость → начальная цена → формат → указанный язык → указанная длительность. Для длительности null проходит как непривязанность к присутствию. Язык и длительность не проверять, если они не заданы.

Для каждой записи сохранить все причины; в итоговой статистике считать только первую по фиксированному порядку. Поэтому:

```text
city_category_total = eligible_count + сумма(rejected_first_reason)
```

Пользовательская формулировка для нескольких причин: «Сначала исключили N занятых; среди оставшихся M с начальной ценой выше бюджета…». Не называть эти группы общим числом всех дорогих/занятых профилей: условия могут пересекаться.

Если допустимых 1–2, объяснить и число показанных, и почему больше нет. Возможна причина «в этом городе в категории всего два профиля» без отсева. Если допустимых больше трёх, написать «условия проходят N, показываем 3».

У площадок тот же механизм календаря. Нельзя обходить занятость для Банкетного зала или Отеля.

## 6. Ranking, AI и объяснения

Сначала нужна работающая базовая версия без обязательного внешнего сервиса. Участник 2 фиксирует простую воспроизводимую формулу и компоненты. Не считать дополнительные языки преимуществом, если они не нужны в запросе. Не выдавать дешевизну за качество. Не выдавать численные веса за обученные или доказанно оптимальные.

AI-модуль, если он реально подключён, сравнивает смысл description и текста из заявленных параметров. Он не получает права изменить дату, бюджет или допуск. Не придумывать пожелания: казахский язык не означает запрос на традиционный той, а свадьба не означает «большая аудитория».

Если модель/API уже настроены, использовать существующие. Данные описаний кэшировать; фиксировать модель/версию, способ подготовки текста и режим. Не подключать тяжёлую новую инфраструктуру ценой основного сценария. Режим работы фиксировать для запуска/демо; запрещён скрытый переход на другой ranking между одинаковыми запросами. Если AI недоступен, базовый режим должен быть явно обозначен, без заявления «ИИ работает».

TF-IDF/ключевые слова — лексическое сопоставление, не понимание смысла нейросетью. Использование Codex для написания кода — не доказательство AI-функции внутри готового сервиса. В README указывать фактически реализованное.

Устойчивый порядок: конечный округлённый score по убыванию → начальная цена по возрастанию → канонический строковый ID. Уникальность ID проверить. Не использовать случайность, текущее время или исходный порядок как скрытый фактор.

Объяснение: 1–2 предложения, минимум два проверяемых факта; один по возможности отличает кандидата. Любое «самый/единственный» требует вычисленной проверки в явно названной группе и учёта равенств. «Не указано в описании» не означает «не умеет». Описание — утверждение профиля, а не независимо подтверждённый опыт; писать «в профиле указано…».

Если профили по доступным фактам одинаковы, не выдумывать различия ради теста. Показать ограничение данных; использовать подтверждённые отличительные фрагменты, где они есть. Не подменять объяснение реального ranking красивым несвязанным преимуществом.

Дата: «по календарю нет отметки о занятости на …» или «свободен по данным каталога», не гарантия брони. Цена: всегда «от». Числа из примеров задания не переносить в выдачу без расчёта.

## 7. Приёмка и README

Нужны реальные воспроизводимые запросы: плотная осенняя категория с >3 допустимыми; редкая; категория отсутствует; категория есть, но не проходит; пара дат с изменением списка именно из-за busy_dates. Две любые даты не обязаны менять TOP-3: подобрать и подтвердить такую пару по данным.

Для пары дат показать конкретный исчезнувший профиль и причину его исключения на второй дате. Не сохранять занятых в рекомендациях. При обычном запросе статистика занятости тоже видна.

Тестировать границы budget == price и duration == max_hours, null, optional=None, одинаковые scores, отсутствующие/повреждённые файлы, некорректные даты, 0/1/2/>3 кандидатов. Отдельно проверить повтор и перезапуск, а не только два вызова в одной сессии.

В README: проблема; быстрый запуск с проверенной версией Python и зависимостями; установка/тесты; архитектура; правила допуска; точная фактическая формула ranking; где AI и где его нет; evidence и примеры; статусы; календарное окно; цена «от» и имputed-флаги; происхождение профилей; проверенные демо; реальные ограничения; распределение авторства. Не писать выдуманное число тестов, подтверждённые метрики или готовность неработающих функций.

Ориентир ответа до 10 секунд проверить измерением на демо-ноутбуке. Отдельно сообщить холодный старт/загрузку модели и время подготовленного запроса. Не обещать универсальную скорость по одному замеру.

# Общий контекст и распределение задач через Codex

Дата подготовки: 23 сентября 2026 года. Проект: #79-lite, подбор event-подрядчиков.

## Что это

Пакет содержит исходное задание, подробную смысловую сводку доступной переписки, актуальное ТЗ, три плана ролей, начальную доску задач и правила координации. Это НЕ дословная выгрузка всей истории ChatGPT, не код приложения, не датасет и не подтверждение готовности проекта.

Пользовательский замысел: контекст хранится в проекте; каждый участник на своём ноутбуке обращается к своему Codex; Codex читает общие требования и фактический код, выбирает конкретную работу в пределах роли, выполняет её и сохраняет проверяемый результат. Участник 3 не принимает технические решения.

## Внедрение — один раз, у участника 1

1. Поместить папку `codex_project_context` в корень действующего Git-проекта. Не заменять приложение, README или существующие инструкции. Все документы пакета — обычный текст UTF-8/Markdown.
2. Открыть именно этот проект в Codex и отправить начальный промпт ниже.
3. Codex участника 1 изучает существующие инструкции и Git, аккуратно добавляет совместимый блок из `AGENTS_APPEND.md` в действующий корневой `AGENTS.md` (или создаёт его при отсутствии). Если `AGENTS.override.md` затеняет файл, учесть это, а не создавать конкурирующие правила. Не менять глобальные настройки и разрешения. При конфликте сохранить действующие инструкции и сообщить точный конфликт.
4. Codex сверяет пакет с реальным состоянием: пути файлов, действующий контракт, ветки, наличие датасета, существующие задачи. Сохраняет работающий код. Планы — не команда переделать архитектуру.
5. Координатор заполняет `CURRENT_STATE.md`, актуализирует назначения в `TEAM_BOARD.md`, не редактируя журналы участников 2 и 3. Непроверенное оставляет непроверенным.
6. Посмотреть diff. Создать коммит только с согласованными контекстными файлами и блоком инструкций; не включать чужие изменения, секреты или `.env`. Опубликовать в согласованную ветку при наличии разрешения. Участник 1 сообщает остальным ветку и hash.
7. Участники 2 и 3 через свои Codex безопасно получают этот коммит в свои рабочие ветки. Не клонируют новый несвязанный проект и не теряют локальные изменения.
8. После добавления инструкций начать новую сессию Codex в проекте либо явно попросить текущую сессию перечитать указанные файлы. Проверка: Codex называет свою роль, реальную ветку, актуальные источники и одну задачу с критериями готовности.

Если старый `codex_team_plan` уже используется, не удалять его автоматически. Участник 1 согласует единый набор активных ссылок на этот пакет; прежние документы остаются историей. Не просить всех агентов выполнять два несовместимых плана одновременно.

```text
Каждому назначь следующую независимую задачу в его роли.
Не выполняй за участников 2 и 3 их изменения.
Потом начни мою ближайшую задачу. Сохраняй отдельные коммиты.
```

## Продолжение — для любого участника

```text
Продолжи мою роль по актуальной доске задач и моему журналу.
Сначала проверь изменения команды. Не повторяй готовую работу.
Выполни следующий доступный шаг, покажи проверку и обнови мой журнал.
```

## Что открывать Codex

Сначала: применимые инструкции → PROJECT_SPEC.md → TEAM_BOARD.md → CURRENT_STATE.md → свой файл roles/PARTICIPANT_N.md → свой progress/PN.md → относящийся к задаче код.

TASK_ORIGINAL.md нужен для точной сверки с организаторами; SESSION_CONTEXT.md — для мотивации и истории решений; COORDINATION.md — для выбора задач, Git и передачи работы. Не читать всю историю заново перед каждой мелкой правкой.

## Граница автоматизации

Это протокол работы с файлами, а не запущенный сетевой диспетчер. Три независимые сессии на ноутбуках не должны предполагать, что они видят чужие несохранённые диалоги и правки. Публикуются коммиты и журналы в общем remote; после получения обновлений Codex перечитывает состояние. Если сеть/доступ недоступны, он сообщает, по какому локальному снимку работает.

Файлы инструкций не блокируют доступ технически. Ограничения ролей подкрепляются отдельными ветками/копиями, проверкой diff и одним интегратором. Права доступа и подтверждения команд сохраняются.

## Первый практический результат

После внедрения у всех троих должно быть общее ТЗ, проверенный контракт, своя ветка, своя следующая задача и единое понимание того, что уже сделано. Не тратить оставшийся хакатон на настройку сложной системы агентов.

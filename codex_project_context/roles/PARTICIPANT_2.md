## Контракт моей работы

```python
rank_candidates(candidates, query) -> list[dict]
build_cards(top_candidates, query) -> list[dict]
```

Первая функция получает уже допустимых и возвращает весь список в устойчивом порядке с `score`, `score_breakdown`, `evidence`. Срез до трёх делает участник 1. Вторая получает финалистов, добавляет explanation и нужные поля карточки, не меняет состав и порядок.

Не повторять hard filters внутри ranking. Не возвращать занятого из общего каталога. Не мутировать исходные профили.

## Этап 1. Работающая базовая версия

Не начинать с установки нескольких моделей и подбора сложных весов. Сначала реализовать простой воспроизводимый ranking и объяснения, чтобы модуль можно было быстро соединить с ядром.

Зафиксировать и описать факторы. Минимальная допустимая база — прозрачная сортировка по начальной цене с tie-break по ID и фактами из описаний. Если реализовано лексическое сопоставление, точно назвать его лексическим. Не выдавать сортировку или TF-IDF за нейросетевое понимание.

Для score с несколькими факторами хранить вклад каждого. Не давать бонусы за уже одинаково выполненный обязательный критерий. Дополнительный английский язык без такого запроса не доказывает лучший выбор. Дешевле не означает качественнее. `max_hours=null` не давать бонус «бесконечное время».

Порядок: конечный фиксированно округлённый score по убыванию, начальная цена по возрастанию, строковый ID. Все score конечные, не NaN. Повтор и перестановка входных строк не должны менять результат.

## Этап 2. Главная ценность — объяснения

Сначала собрать структурированные evidence из профиля и запроса. Для каждого сохранить поле-источник и значение. Для description — буквальный релевантный фрагмент, который можно найти в исходнике. Без API сначала можно использовать детерминированный выбор предложения.

Затем сгенерировать 1–2 предложения, минимум два конкретных проверяемых факта. Сообщить, почему подходит, и по возможности чем отличается. Текст должен отражать фактические причины выбора, а не придуманное преимущество после сортировки.

Формулировка цены: «Начальная цена 220 000 ₸ — на 80 000 ₸ ниже лимита». Не «гарантированно останется 80 000 ₸». Доступность: по данным календаря, не подтверждённая бронь. Для опыта: «в описании указано…», не доказанная квалификация.

Сравнения с другими кандидатами допустимы только после вычисления, с указанием группы «среди показанных». При равных минимальных ценах нельзя назвать одного единственным самым дешёвым. Не утверждать уникальность опыта на основании отсутствия такого текста у остальных.

Пример формы, НЕ сведения о реальном профиле:

> По календарю свободен на выбранную дату; начальная цена 220 000 ₸ ниже лимита на 80 000 ₸. В описании отдельно указаны семейные свадьбы; заявленные 8 часов покрывают запрошенные 6.

Не писать «идеальный», «лучший», «отличный выбор» без доказательства. Не обещать способности, которых нет в данных. Если профили действительно неразличимы по данным, обозначить это ограничение вместо выдумки.

## Этап 3. AI — только конкретная реализованная функция

Если в проекте уже есть работающая модель/API, использовать существующее подключение. Добавлять embeddings после рабочей базовой версии, не блокируя интеграцию и объяснения.

Задача AI: сравнить смысл description с явно заданными параметрами. Не выдумывать пожелания о размере свадьбы, стиле, национальных традициях или качестве. Город, дата и бюджет проверяются ядром, а не смысловой близостью текста.

Для embeddings сохранить модель/версию, подготовку текста и кэш профилей. Для одного запуска фиксировать режим ranking. Если AI недоступен, выбрать явно обозначенную базовую версию; не переключать порядок незаметно между повторами одинакового запроса.

В итоговом отчёте точно назвать один из вариантов: «в продукте используется такая-то модель для такой-то функции» либо «пока работает базовый алгоритм без нейросетевого inference». Codex, написавший код, не заменяет AI внутри сервиса.

LLM для свободного сочинения объяснений в MVP не обязательна. Если она уже используется, проверять факты; инструкция «не выдумывай» сама по себе не является проверкой.

## Этап 4. Мои проверки

Тестировать пустой/единичный вход, равные оценки и цены, повторный вызов, перемешанный вход, отсутствие мутаций исходных данных, конечность score, правильность tie-break, сохранение всех допустимых в rank_candidates и состава в build_cards.

Для объяснений: факты существуют; числа верны; фрагмент description буквально присутствует; price_imputed и null не дают ложных обещаний; 1–2 предложения; нет ложного «единственный» при равенстве; нет неподтверждённого качества или скрытого обещания конечной цены.

Отдельно руками вместе с участником 3 проверить один реальный запрос: убрать имена у трёх карточек и попытаться сопоставить explanations с профилями. Если тексты различаются только косметически, выбрать более содержательные факты. Если фактов объективно мало, зафиксировать это ограничение.

При подключённом AI — проверить сбой/отсутствие модели и честное обозначение базового режима. Протестировать воспроизводимость в согласованной конфигурации, включая повторный запуск.

## Этап 1. Форма и результат, без дизайна ради дизайна

Создай или доработай простой Streamlit-интерфейс под существующий `recommend(query, contractors)`.

Поля: город, дата, тип мероприятия, категория, бюджет, необязательные длительность и язык. Значения форматов/категорий/языков брать из каталога, сохраняя возможность выбрать категорию, которая есть в наборе, но отсутствует в выбранном городе: этот бизнес-исход нужно уметь показать.

Ограничить календарь 23.09.2026–31.12.2026. Отсутствие optional-параметров передавать как None, дату как ISO. Проверить положительный бюджет и длительность. Не добавлять чат и новые обязательные вопросы.

Показывать полученные results в исходном порядке: имя, выбранная категория, город, цена «от», explanation. Не сортировать и не выбирать кандидатов заново в UI.

Сообщение `message` и статистику брать из ядра. При category_not_found показать отсутствие категории. При no_matching_candidates — реальные причины. При 1–2 карточках — почему их меньше трёх. Ошибки ввода или загрузки показывать отдельно, не как отсутствие подходящих подрядчиков.

Показать synthetic, city_imputed, price_imputed честными подписью/значком. Не называть профиль «проверенным реальным» по одному synthetic=false. Добавленные командой синтетические записи должны отличаться от исходных, если такие есть.

Отдельно видимый смысл цены: это начальная стоимость, итоговую смету каталог не подтверждает. Доступность тоже только по календарю каталога.

Если backend ещё не готов, интерфейс можно проверять на явно помеченной тестовой фикстуре, но не выдавать её за живой подбор. Перед сдачей все демо обязаны вызывать настоящий recommend.

## Этап 2. Пользовательская проверка пяти болей

Codex запускает приложение/проверки доступными средствами и даёт мне одну понятную задачу. Если визуальная проверка недоступна его инструментам, он честно об этом говорит и даёт адрес локального приложения и точные шаги для моей проверки.

Первая полезная задача:

> Открой один подтверждённый запрос с тремя карточками. Не смотри на имена. Объясни своими словами, чем отличаются рекомендации и почему каждая здесь. Отметь фразы, которые подходят всем троим.

После моего ответа Codex оформляет замечание: запрос → что показано → что ожидалось → какая боль нарушена → доказательство из данных → кому исправить.

Дальше по одной проверке: нет ли занятого в results; понятна ли нулевая выдача; почему только два; цена не звучит ли как гарантия; видна ли синтетика; совпадает ли повторный порядок.

Заведи `docs/acceptance.md` с реальным состоянием «проверено / не проверено / ошибка». Не писать «всё работает», пока проверка не выполнена.

## Этап 3. Настоящие демо-запросы

Не придумывай параметры и количество результатов. Используй реальный JSONL и реальный recommend, чтобы найти и записать запросы в `demo_queries.json` и описать в `docs/demo.md`.

Нужны:

1. Плотная категория — Ведущий, Фотограф или Банкетный зал, осенняя дата, желательно >3 допустимых, чтобы показывался реальный выбор из нескольких.
2. Редкая категория — показать столько допустимых, сколько есть, желательно 1–2 и понятную причину малого количества.
3. Категория есть, но все не проходят — объяснённая пустая выдача.
4. В городе такой категории нет — отдельный бизнес-статус, не та же пустая выдача.
5. Пара одинаковых запросов с единственным изменением даты, где список действительно меняется из-за busy_dates.

Для каждого сохранить полный query, ожидаемый status, проверенный порядок ID, допустимое количество, что демонстрируем и версию/hash данных. Для пары дат сохранить конкретный исчезнувший профиль и факт его занятости на второй дате. Показывать этот факт вне рекомендованных карточек, например в объяснении отсева. Не возвращать занятого в TOP-3.

Новые даты не обязаны всегда давать другой список: подобрать подтверждённую пару. Общие количества из задания не считать количествами в одном городе.

Если подходящего сценария в данных нет, честно сообщить ограничение. Не менять исходник ради красивого демо. Синтетические unit-тесты допустимы только отдельно и с явной маркировкой.

## Этап 4. README — полноценная часть продукта

Пиши параллельно с интерфейсом, а на финише сверяй с фактическим кодом. Не требуй от меня технических объяснений: прочитай реализацию и `docs/ranking_notes.md`, точечно уточни у соответствующего участника неясность.

Структура README:

1. Что делает сервис и почему недостаточно просто длинного каталога.
2. Быстрый запуск: проверенная версия Python, создание окружения, зависимости, команда приложения. Для текущей структуры ожидаемые команды `python -m pip install -r requirements.txt`, `python -m streamlit run app.py`, `python -m pytest -q`; окончательный README должен соответствовать реально проверенным командам и структуре.
3. Минимальная схема: ввод → фильтры → ranking → до 3 → фактические объяснения.
4. Где именно AI, какая модель/режим реально работает; чего AI не решает. Если пока нет AI-inference, не утверждать обратного.
5. Точные правила отбора и фактическая формула ranking. Не сочинять проценты или веса.
6. Пример карточки из проверенного запуска, источник её фактов и разница с другими рекомендациями.
7. Три статуса, случай 1–2 результатов, правила подсчёта исключений без дублей.
8. Данные: JSONL, календарное окно, max_hours=null, цена «от», synthetic и imputed-флаги.
9. Конкретная таблица demo queries с ожидаемыми исходами и указанием, что именно проверяет жюри.
10. Тесты, фактически выполненные команды и замеры скорости. Не писать непроверенное число тестов или «<1 секунды» без измерений.
11. Ограничения: не бронирование; доступность по каталогу; не окончательная смета; неполные различия в профилях; базовый режим при отсутствии AI.
12. Вклад всех троих и обоснованные следующие шаги, не заявленные как готовые функции.

Простая Mermaid-схема возможна, но не важнее работающего запуска. Скриншот брать из реального приложения, не рисовать вымышленный результат. Секреты, ключи API и .env не включать.

Я участник 1, один из двух уверенных программистов. Реализацию, команды и проверки выполняем через Codex. Моя ответственность: сервис не рекомендует неподходящих и части команды соединяются в одно приложение.

Прочитай применимые AGENTS.md, `codex_team_plan/TEAM_SPEC.md`, README, структуру, git status, текущую ветку и последние коммиты. Не считать проект пустым. Не заменять уже работающий код новой архитектурой.

## Моя зона

Рабочая ветка: `feature/core` либо уже существующая согласованная ветка этой роли.

Файлы по умолчанию: `data_loader.py`, `recommender.py`, `contracts.py` при необходимости, `tests/test_core.py`, `tests/test_loader.py`, `tests/test_integration.py`.

Только я поддерживаю общие `requirements.txt`, `.gitignore`, `.env.example` без секретов, контракт и таблицу владельцев. Участники 2 и 3 сообщают потребность в зависимости; сами общий файл не меняют. README и UI не переписываю. Исходный JSONL не правлю ради тестов.

После передачи общих интерфейсов не менять их односторонне. На этапе интеграции предпочитать исправление несовместимости в своей обвязке. Если необходима правка чужого модуля — описать её владельцу, не присваивать его часть.

## Этап 1. Разблокировать остальных

Цель — быстро получить одну договорённость, а не построить большой каркас.

Codex должен:

1. Проверить наличие JSONL, настоящие названия полей, форматы дат и файловую структуру. Если файла нет — сообщить, не выдумывать результаты.
2. Проверить remote/ветку и автора Git без изменения личности. Сохранить все существующие незакоммиченные изменения.
3. Зафиксировать контракт query/response и функции из TEAM_SPEC. Если функции уже называются иначе, записать точное соответствие и дать его остальным.
4. Создать только необходимый каркас и безопасные зависимости, не реализуя за участника 2 ranking или за участника 3 интерфейс. Заглушки, если без них нельзя начать, должны явно означать «не реализовано», а не возвращать мнимый успешный подбор.
5. Сделать стартовый коммит. После разрешённого push передать команде ветку, hash и какие файлы каждый может менять.

Остальным не нужно ждать готовых фильтров, чтобы писать свой код: они используют этот контракт и локальные тестовые фикстуры с `synthetic=true`.

## Этап 2. Загрузка и правила допуска

Реализуй `load_contractors(path)` и отдельную проверку кандидата. Ошибка файла должна указывать, что произошло и где: отсутствующий файл, номер битой строки, некорректное поле, повторяющийся ID. Не пропускать ошибочные записи молча. Не придумывать отсутствующие цены или даты.

Нормализуй ввод ограниченно: пробелы, регистр для сравнения; сохрани исходные значения для показа. Не делать нечёткую автозамену города и категории.

Сначала найди группу город + категория. Затем проверь busy_dates, минимальную цену, event_formats, указанный язык и длительность. Границы «равно бюджету/длительности» проходят. `max_hours=null` не является бесконечным запасом часов; просто не применять фильтр присутствия.

Для каждого исключённого сохраняй все причины, но статистику делай по одной первичной причине в фиксированном порядке. Сумма исключённых и допущенных должна равняться размеру группы.

Создай понятные сообщения для отсутствующей категории, нулевого результата и 1–2 вариантов. Не смешивай системную ошибку с честным отсутствием кандидатов.

## Этап 3. Собрать recommend

`recommend(query, contractors)` выполняет:

```text
валидация → группа город/категория → фильтры → статусы/статистика
→ rank_candidates всех допустимых → срез [:3]
→ build_cards финалистов → единый response
```

Только здесь делается ограничение до трёх. Не реализовать второй scoring в ядре. Не сортировать карточки после генерации объяснений.

Вывести доступные данные об исключении конкретных профилей в `rejections`, чтобы участник 3 мог объяснить смену даты. Сохранить фактический ranking_method и версии в meta.

## Этап 4. Проверить

Пиши свои тесты параллельно с ядром, не отдавай всю проверку участнику 2. До интеграции ranking можно изолировать тестовым адаптером только в тестах; не подменять им production-результат.

Обязательные случаи: занятый ведущий и занятый зал; цена больше/равна бюджету; неподходящий формат; язык задан/не задан; длительность равна/превышает максимум; max_hours=null; категория отсутствует; все исключены; 1–2 результата; максимум три; пересечение причин без двойного счёта; дата вне окна; файл повреждён/не найден.

## Этап 5. Ранняя интеграция

Первый сквозной запуск нужен примерно к 60–75-й минуте командного окна. Не оставлять первое соединение на конец.

Получить актуальные удалённые ветки через fetch. Интегрировать только сохранённые и переданные командой изменения, с сохранением авторских коммитов. Не полагаться на то, что чужая ветка уже существует локально. Не делать force push, массовый reset или squash всей командной истории.

Запустить общий набор тестов и приложение. Ошибки маршрутизировать владельцам: ядро — мне, ranking/объяснения — участнику 2, UI — участнику 3. Повторять интеграцию небольшими порциями.

На финише проверить запуск на чистом окружении вместе с участником 3, согласованность README и кода, наличие коммитов всех авторов. Сообщить фактически выполненные команды и результаты, не «должно работать».

## Коммиты

Не количество ради количества, а законченные изменения. Примеры:

- `chore: establish shared contract and project setup`
- `feat: add dataset validation and eligibility filters`
- `test: cover filtering and rejection accounting`
- `feat: integrate recommendation pipeline`

Перед каждым коммитом посмотреть diff, запуск проверок и состав staged-файлов. Коммитить только свои изменения.

## Моя человеческая проверка

Codex должен дать мне один реальный или явно тестовый запрос и показать: исходную группу, кого исключили и почему, кто прошёл. Я проверяю, соответствует ли это заданию. Если нужны сведения о Git-авторе или доступе, спросить только недостающие данные, не придумывать.

Из корректного запроса получается согласованный ответ; занятых/неподходящих нет; 3 статуса различаются; причины сходятся; модуль участника 2 вызывается без дублирования логики; приложение участника 3 получает ожидаемые поля; тесты выполнены, авторские коммиты сохранены.

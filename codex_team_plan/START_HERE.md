# Три участника · один проект · работа через Codex

Это план работы, а не отчёт о готовности репозитория. Текущий код и исходный JSONL в этом пакете отсутствуют. Codex должен сначала проверить ваш реальный проект.

## Как начать

Положите папку `codex_team_plan` в корень существующего проекта. Не создавайте вместо проекта новый репозиторий. Участник 1 первым читает свой план, сверяет его с текущим кодом и фиксирует общие интерфейсы. После общего стартового коммита участники 2 и 3 получают его в своих локальных копиях и начинают параллельную работу.

Короткие сообщения для трёх отдельных сессий:

**Участник 1**

> Я участник 1. Прочитай применимые AGENTS.md, codex_team_plan/TEAM_SPEC.md и codex_team_plan/PARTICIPANT_1.md. Изучи репозиторий и git status. Сохрани готовую работу. Зафиксируй общий контракт, затем выполни мой план в моей ветке: реализация, проверки, отчёт и отдельные коммиты.

**Участник 2**

> Я участник 2. Прочитай применимые AGENTS.md, codex_team_plan/TEAM_SPEC.md и codex_team_plan/PARTICIPANT_2.md. Изучи текущий код и согласованный контракт. Выполни мой план в моей ветке: ранжирование, объяснения, проверки и отдельные коммиты. Не изменяй чужие файлы.

**Участник 3**

> Я участник 3, специалист по предметной области. Прочитай применимые AGENTS.md, codex_team_plan/TEAM_SPEC.md и codex_team_plan/PARTICIPANT_3.md. Код и документацию делай сам в моей ветке. Мне объясняй простыми словами и давай по одной пользовательской проверке. Не проси меня выбирать технические решения.

## Общая картина

```text
Участник 1: данные → обязательные фильтры → допустимые кандидаты
                                       ↓
Участник 2: оценка → устойчивый порядок → факты для объяснений
                                       ↓
Участник 1: максимум 3 → вызов генератора карточек → единый ответ
                                       ↓
Участник 3: интерфейс → пользовательская проверка → демо → README
```

Важное разделение: участник 2 возвращает весь упорядоченный список допустимых кандидатов. Только участник 1 делает срез до трёх. Генератор объяснений участника 2 получает именно эту финальную тройку. Интерфейс ничего не ранжирует и не фильтрует повторно.

## Владение файлами

| Участник | Основная зона | Не трогает |
|---|---|---|
| 1 | Контракт, загрузка, фильтры, общий ответ, зависимости, интеграция | Самовольное переписывание ranking, объяснений, UI и README |
| 2 | Ранжирование, смысловое сравнение, объяснения, свои тесты | Загрузку, правила допуска, общий контракт, UI, README, общие зависимости |
| 3 | UI, README, демо, приёмочные проверки | Фильтры, scoring, общий контракт, общие зависимости |

Если названия файлов уже другие, участник 1 один раз фиксирует соответствие. Не переименовывайте работающий проект ради совпадения с этим планом.

## Общие правила работы

У каждого — своя локальная копия одного репозитория, одна рабочая ветка и одна основная сессия Codex. Участник 1 интегрирует результаты. Не запускайте две пишущие сессии над одними и теми же файлами.

Codex сначала читает инструкции и `git status`, затем выполняет ограниченный этап, запускает проверки, смотрит diff и делает содержательный коммит только своих изменений. Существующие незакоммиченные изменения не удалять. Не использовать `git add .` без просмотра содержимого, `reset --hard`, `clean -fd`, force push или переписывание чужой истории.

Коммитить под реально настроенными именем и email участника. Не выдумывать авторов. Если автор не настроен, объяснить, какие личные данные нужны для Git. Push — только в свою согласованную ветку, когда команда разрешила публикацию; не обходить запросы разрешений среды.

После этапа сообщать: что готово, что реально проверено, какой коммит создан, есть ли блокер и кому он адресован. Ошибка чужого модуля — точное сообщение владельцу, а не переписывание его кода.

## Контрольные точки в пределах трёхчасового окна

Это распределение времени команды, а не обещание длительности работы Codex. Если часть времени уже прошла, продолжайте с фактически выполненного этапа — не начинайте заново.

| Время от старта | Участник 1 | Участник 2 | Участник 3 |
|---|---|---|---|
| 0–10 мин | Сверяет проект, фиксирует контракт и зависимости, общий стартовый коммит | Читает данные и требования | Читает задание и проверяет пользовательский сценарий |
| 10–60 мин | Загрузка, фильтры, статусы, свои тесты | Базовый ranking, факты, объяснения, свои тесты | Простая форма и карточки, черновик README |
| 60–75 мин | Первая интеграция и запуск целиком | Исправляет свой модуль | Проверяет реальный результат в интерфейсе |
| 75–130 мин | Исправляет фильтры и интеграцию | Улучшает объяснения; AI только без риска для основной версии | Реальные демо-запросы и README по фактическому коду |
| 130–160 мин | Общие тесты, проверка запуска | Повторяемость и доказательства объяснений | Все демо, проверка README с чистого окружения |
| 160–180 мин | Финальный merge и проверка истории | Только исправления | Финальная документация и репетиция |

Не ждать окончания всех трёх модулей для первого соединения. После первого рабочего сквозного запуска не менять архитектуру. Последние 20 минут — без новых технологий.

## Проверки перед сдачей

Плотная категория с более чем тремя допустимыми кандидатами; редкая категория; категория отсутствует в городе; категория есть, но все исключены; два запроса с изменением только даты, где выдача действительно меняется из-за календаря; повторный запрос с тем же порядком. Все параметры брать из реального JSONL, не из выдуманных примеров.

Объяснения — 1–2 предложения из данных. Цена «от» не превращается в гарантированную смету. Синтетические и подготовленные значения не выдаются за проверенные реальные сведения. Скорость измерена, а не обещана.

## Основания для организации работы

Требования продукта и оценка — из задания #79-lite, предоставленного командой. Общие практики Codex — официальная документация OpenAI: «Custom instructions with AGENTS.md» и «Best practices» (проверены 23.09.2026). Для этого проекта длинные требования вынесены в обычные Markdown-файлы и читаются явно. Существующий AGENTS.md нельзя перезаписывать этим пакетом.

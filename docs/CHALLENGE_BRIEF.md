## Официальное задание

- Точное название: «Хакатон-задача: умный подбор подрядчиков (#79-lite)».
- Точный текст или ссылка на предоставленный файл: `docs/HackAlem AI_ Хакатон-задача_ умный подбор подрядчиков.pdf`.
- Обязательный результат: сервис принимает город, дату, тип мероприятия, категорию и бюджет, опционально длительность и язык; возвращает до 3 карточек с именем, категорией, городом, ценой и 1–2 предложениями конкретного объяснения.
- Ограничения: занятые на дату не попадают в выдачу; меньше трёх — показывать сколько есть и почему; одинаковый запрос даёт одинаковый порядок; различать успех, отсутствие категории в городе и отсутствие прошедших условия кандидатов; бронирование, заявки и уведомления не входят.
- Предоставленные данные и сервисы: официальный CSV на 66 профилей и HTML-превью. PDF также называет JSONL, но этого файла в репозитории нет. Внешний сервис для базовой версии не требуется.
- Критерии оценки: соответствие и работоспособность — 25; техническая реализация — 25; README и воспроизводимость — 25; ценность и применимость — 15; развитие и оригинальность — 10.
- Способ технической проверки: живые запросы для плотной и редкой категории, запрос без результата, повторяемость порядка и две даты со сменой выдачи из-за `busy_dates`; ориентир ответа до 10 секунд.
- Неясности, требующие обращения к организатору: условия публикации датасета вне хакатона; является ли отсутствующий JSONL обязательным артефактом, если официальный CSV содержит все заявленные поля.

## Минимальный продукт

- Основной пользователь: заказчик мероприятия, уже выбравший город и тип мероприятия.
- Проблема или задача пользователя: выбрать до трёх подходящих подрядчиков из существующего каталога и понять причины выбора.
- Один полный сценарий: пользователь задаёт параметры → ядро валидирует запрос → выбирает город/категорию → исключает занятых и неподходящих → ranking получает всех допустимых → ядро берёт первые три → генератор карточек объясняет финалистов.
- Видимый результат: единый ответ со статусом, 0–3 карточками, статистикой первичных причин исключения и конкретными исключёнными профилями.
- Как проверить правильность: каждый результат проходит обязательные фильтры; `city_category_total = eligible_count + сумма(rejected_first_reason)`; срез до трёх выполняется только в `recommend`; повтор не меняет порядок.
- Что сознательно не делаем: UI, бронирование, расширение города, добавление профилей ради TOP-3, scoring и объяснения участника 2.

## Общие контракты

Заполнять только после выбора решения и до параллельной реализации.

- Граница системы: локальный каталог → валидация и обязательные фильтры → внешний модуль ranking/карточек → единый словарь ответа; UI только отображает его.
- Компоненты: `contracts.py` (Pydantic-модели и ошибки), `data_loader.py` (CSV/JSONL), `recommender.py` (валидация запроса, фильтры, статусы и интеграция), `ranking.py` участника 2, UI участника 3.
- API и форматы данных: публичные `load_contractors(path) -> list[dict]`, `recommend(query, contractors) -> dict`, `rank_candidates(candidates, query) -> list[dict]`, `build_cards(top_candidates, query) -> list[dict]`. Точная схема query/response остаётся в `codex_team_plan/TEAM_SPEC.md`; Pydantic-схемы — в `contracts.py`.
- Хранение данных: официальный `docs/hackathon dataset anonymized .csv`; загрузчик также принимает официальный формат `.jsonl`. Исходный датасет не изменяется.
- Внешние сервисы: отсутствуют в базовой версии.
- Переменные окружения без значений секретов: не требуются для ядра.
- Детерминированный пример или резервный режим: обязательные фильтры полностью локальны; успешная выдача до интеграции честно завершается `IntegrationNotReadyError`, а не мнимым результатом.

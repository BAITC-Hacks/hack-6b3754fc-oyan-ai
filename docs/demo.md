# Демо: сценарий защиты и доказательства

Статус: реальные прогоны пока не выполнены. В этой ветке есть интерфейс, но нет JSONL и настоящего `recommend`. Ниже план проверки, а не отчёт об успешном подборе. Учебные карточки из UI-тестов не показывать как результат продукта.

## Перед демонстрацией

Интегратор подключает `data_loader.load_contractors(path)` и `recommender.recommend(query, contractors)`, добавляет согласованный JSONL и зависимости. Участник 2 передаёт реальное правило ранжирования и режим AI в `docs/ranking_notes.md`.

После интеграции участник 3 запускает настоящий подбор и заполняет `demo_queries.json`: полный query, status, ordered_ids, eligible_count, returned_count, message, dataset_hash, scoring_version, ranking_method и время вызова. До этого список verified_cases остаётся пустым. Нельзя получить ожидаемый порядок, просто отсортировав CSV вместо вызова ядра.

При смене данных или режима прежние ожидания проверить заново. Сверить hash фактического файла и `meta.dataset_hash`; алгоритм hash должен быть указан интегратором.

## Последовательность показа (около 4 минут)

| Шаг | Что делаем | Что должно быть доказано |
|---|---|---|
| 1 | Осенняя дата, Ведущий / Фотограф / Банкетный зал | Более трёх допустимых, показаны три; объяснения связаны с запросом и различаются |
| 2 | Повторяем запрос без изменений | Порядок ID совпадает |
| 3 | Меняем только дату на заранее проверенную | Конкретный прежний финалист занят; его нет в карточках, причина видна в блоке отсева |
| 4 | Редкая категория | Показаны реально допустимые 1–2, объяснено малое количество |
| 5 | Категория есть, но никто не проходит | Понятные причины, корректный подсчёт без дублей |
| 6 | Категории нет в городе | Отдельное сообщение об отсутствии категории |
| 7 | Открываем README | Где запуск, тесты, ограничения и доказательства выполненных проверок |

Отдельно перезапустить процесс и повторить плотный запрос. Измерить холодную загрузку отдельно от подготовленного вызова. Ориентир ответа — до 10 секунд на машине демонстрации, а не гарантия для всех компьютеров.

## Как проверять объяснения

Для одного подтверждённого запроса с тремя карточками убрать из рассмотрения имена и попытаться объяснить, почему каждый кандидат здесь. Каждое утверждение сверить с запросом и полями профиля; для description — с буквальным фрагментом. Не считать дополнительный ненужный язык автоматическим преимуществом и не выдавать начальную цену за итоговую.

Синтетический профиль должен быть обозначен. Для проставленной цены или города должна быть отдельная подпись. Если данных для содержательных отличий мало, это ограничение, а не повод придумать преимущество.

## Формат замечания участника 3

- Запрос: все семь полей, включая None.
- Показано: ID и точная фраза / число / порядок.
- Ожидалось: одно конкретное изменение поведения.
- Доказательство: поле профиля, строка календаря или результат повторного вызова.
- Почему важно: какая из пяти болей нарушена.
- Владелец: фильтр/статистика — участник 1; порядок/объяснение — участник 2; отображение — участник 3.

Технический способ исправления пользователь выбирать не должен.
